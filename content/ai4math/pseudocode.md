# 用中间层链接人与计算机

AI4Math 的问题是，AI 直接写 lean4 代码，人看不懂；直接写自然语言（包括用自然语言推理），可能出现幻觉，需要大量智能体不断审核。而且即使 convience 了人类，也可能出错。

人类难以理解，这可能是因为

- 模型本身也不理解这个证明，仅仅是找到了它。
- 模型能够有某种理解，但是模型的写作能力太差。

另一个困难是难以验证正确性，需要转写成 lean 。但是这个转写过程是否确实正确，lean 代码是否可能证明了一个正确的但偏移、失真版本的结论？动辄百万行的 lean 代码没有任何可读性。

一方面，需要让结果能被人理解；另一方面，要能翻译到形式化验证。

## 作为代码的论文

其实过去人类文章也很难读，不知道思路从何而来，各个定理关系是什么。  
由于有一些 C 语言基础，所以我会用 C 的代码思路来读文章。将需要证明的主定理视作 `main()` 函数，其他引理等是被引用的函数。
现在有很多论文本身就是这个风格写作：先在 `Introduction` 章节声明主定理，在靠前的部分声明定义、记号等（`#define`），文章主体是引理、命题，在结尾 `Proof of Main Theorem` 的章节很短，往往是把前面的命题组装起来得到结论。
比较大的区别大概是 `reference` 放在结尾，而不是像 `#include xxx` 一样放在开头。

一个命题是形如 $A \implies B$ 的格式，把它看作函数，有输入和输出（都是statement），这个结构就像 C 语言的函数，对输入的格式有要求，函数本身的输出也有要求。

## 伪代码

计算机领域有一条名言：没有什么问题是加一个中间层解决不了的，如果有，就再加一条。

加一个中间层，一个伪代码风格的，更简单直接的内容。

它应该是一种协议，一个定理/引理/命题的格式，但是并非代码格式，要更宽松一些。
能更好地被人以自然语言风格理解，这同样意味着能被 LLM 思考。  
另一方面，这个*伪*代码应该有严格的部分，使得它依然可以有 `lsp` `ast`，来初步保证正确性。

## 格式化输出

有一种说法，叫数学语言。在数学内部，也有代数几何的语言、层论的语言、Topos 的语言等。
可以尝试将模型（后）训练成使用这种小范围语言。

没有理由和必要用 markdown 式的自然语言输出，而是可以用结构化输出（比如最常用的 json ）。
先从已有的常见的论文写法入门。比如说

- Suppose, Let xxx be, Assume
- Then xxx is xxx
- The following are equivalent

很明显有 `statement` 和 `implies` 两种内容，`statement` 本身也可能是个 `implies` 结构（这里有点类型论的味道），`implies` 两端未必是单数。

从数学论文排版软件来获取灵感也许也是个方法。
另外从程序类型来看，`statement`像是个对象，`implies`像是个函数。应考虑面向对象编程，还是面向过程编程，或者函数式编程的风格呢？

## 实现层面

这个目标可以在多个层次去尝试。

最底层的，我们可以直接修改模型架构，制造数学专用模型。参考多模态模型，或者 VLA 和 JPEA 模型那样，直接把输出部分的 token 限制为 lean 和这个伪代码/语言，并且让两个强绑定。  
另外就是在 agent 和 harness 层面，设计一个伪代码的 prompt，让模型输出这个伪代码，并且在这个伪代码上做一些验证。

另一个模型层面的修改，是考虑 dllm 扩散语言模型，或者以这个思路为中心的非自回归的文本生成方式。

另见[扩散式生成agent](/ideas/diagent)。
